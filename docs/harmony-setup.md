# HarmonyOS setup

This is the HarmonyOS shell for the React Native port. It loads a native
splash, then hands the window to the RNOH surface that renders `App.tsx`
(`商品列表` → `商品详情` → `购物车`, see
[features/cart-and-detail.md](features/cart-and-detail.md)).

The app is a standalone RN 0.72.5 project, not a checkout of
`ohos_react_native`, so it does **not** use the official tester's `file:`
dependencies or its in-repo `react_native_openharmony` module.

## What is wired where

| Path | Role |
| --- | --- |
| `harmony/AppScope/app.json5` | App identity. `bundleName` is `com.example.kmp.rn.harmony` (the KMP app uses `com.example.kmp`, Android/iOS RN use `com.example.kmp.rn`, so all three install side by side). |
| `harmony/AppScope/resources/` | App icon and app label (`KMP RN Demo`). |
| `harmony/build-profile.json5` | Product/module list, `compatibleSdkVersion 5.0.0(12)`, `targetSdkVersion 6.0.0(20)`, and an empty `signingConfigs` placeholder. |
| `harmony/hvigorfile.ts` | Root hvigor project (`appTasks`). |
| `harmony/hvigor/hvigor-config.json5` | hvigor model/execution settings. No RNOH hvigor plugin is needed here (see below). |
| `harmony/oh-package.json5` | Root ohpm project. |
| `harmony/entry/build-profile.json5` | Entry module: stage mode, `externalNativeOptions` pointing at the CMake file, `arm64-v8a` only. |
| `harmony/entry/oh-package.json5` | Dependencies `@rnoh/react-native-openharmony: "0.72.140"` from the ohpm registry and the manually linked `@react-native-oh-tpl/react-native-webview` har. |
| `harmony/entry/src/main/module.json5` | Entry ability, pages profile, `ohos.permission.INTERNET`, start window. |
| `harmony/entry/src/main/ets/entryability/EntryAbility.ets` | Extends RNOH's `RNAbility`; loads `pages/Splash` first. |
| `harmony/entry/src/main/ets/pages/Splash.ets` | Native splash (logo, `KMP RN Demo`, `React Native`); after `SPLASH_MILLIS = 1000` it replaces itself with `pages/Index`. |
| `harmony/entry/src/main/ets/pages/Index.ets` | RNOH `RNApp`; app key `KmpPlaygroundRn`, CAPI architecture enabled, Metro/sandbox/resource bundle providers. |
| `harmony/entry/src/main/ets/PackageProvider.ets` | ArkTS native package list; registers the WebView adaptation's `WebViewPackage` (see [features/webview.md](features/webview.md)). |
| `harmony/entry/src/main/cpp/CMakeLists.txt` | Builds `librnoh_app.so` from RNOH sources in `entry/oh_modules` plus `PackageProvider.cpp` and `RNOHAppNapiBridge.cpp`, and links the WebView adaptation's `rnoh_webview` target. |
| `harmony/entry/src/main/cpp/PackageProvider.cpp` | C++ native package list; registers `WebViewPackage` from the WebView adaptation. |
| `harmony/entry/src/main/resources/rawfile/` | `bundle.harmony.js` and assets generated by `npm run dev`; ignored by git. |

The three splash screens use one set of constants and one visual language:
white background, a `KMP` text logo on `#2563EB`, title `KMP RN Demo` and
subtitle `React Native`. `SPLASH_MILLIS` is duplicated in
`SplashActivity.java` (Android), `SplashViewController.m` (iOS) and
`Splash.ets` (HarmonyOS) because the platforms cannot share a constant, and the
three values must stay equal.

## Building

> **Generate the JS bundle before `assembleHap`.** `bundle.harmony.js` is a
> gitignored build product. Without it the HAP still builds, installs and
> starts, but the app shows only the red screen
> `None of the provided JSBundlePath(s) ... Is Metro server running?`.
> `npm run dev` writes the bundle to
> `harmony/entry/src/main/resources/rawfile/`.

Prerequisites: DevEco Studio (this machine uses 26.0.0 with the API 26 SDK),
ohpm and hvigor on `PATH`, Node/npm, and the JS dependencies installed
(`npm ci`).

```sh
# 1. JS bundle for the harmony platform (must happen before assembleHap)
npm run dev

# 2. RNOH har from the ohpm registry (installs every module's dependencies)
cd harmony
ohpm install --all

# 3. optional: sign for a local installable build
# The committed build-profile has no signing material; this injects the
# machine-local ~/.ohos/dsh-signing-rn.json5 block for the build.
python3 ../scripts/inject-signing.py

# 4. build the HAP
export DEVECO_HOME=/Applications/DevEco-Studio.app/Contents
export DEVECO_SDK_HOME=$DEVECO_HOME/sdk
export OHOS_SDK_HOME=$DEVECO_HOME/sdk/default/openharmony
export HOS_SDK_HOME=$DEVECO_HOME/sdk/default
export RNOH_C_API_ARCH=1
export PATH="$DEVECO_HOME/tools/hvigor/bin:$DEVECO_HOME/tools/ohpm/bin:$DEVECO_HOME/tools/node/bin:$DEVECO_HOME/jbr/Contents/Home/bin:$PATH"
hvigorw --mode module -p product=default -p buildMode=debug assembleHap --no-daemon
```

A local signed build writes
`harmony/entry/build/default/outputs/default/entry-default-signed.hap`; install
it with `hdc install -r <hap>` or `devecocli device app install <hap> --replace`.

A build without signing (the CI compile gate) writes
`entry-default-unsigned.hap`. hvigor skips signing when `signingConfigs` is
empty and prints a warning, but the compile/package still succeeds. The
committed `build-profile.json5` therefore builds unsigned out of the box and
needs no signing material in CI.

After a local signed build, restore the empty placeholder before committing:
`git checkout -- harmony/build-profile.json5`.

## CI

- `js` runs on GitHub-hosted infrastructure: `npm ci`, `npx tsc --noEmit`,
  `npm test`.
- `android` runs on the repository self-hosted runner
  (`self-hosted, macOS, ARM64`): `npm ci`, writes
  `android/local.properties` with `sdk.dir=$ANDROID_HOME`, then
  `./gradlew :app:assembleDebug`.
- `harmony` runs on the same runner: `npm ci`, **`npm run dev`** (the bundle is
  required before packaging), `cd harmony && ohpm install --all`, then
  `hvigorw ... assembleHap` and verifies the unsigned HAP exists. The runner
  has no signing material, so this is a compile/package gate, not a signed
  installable artifact.
- `ios` stays disabled with a comment until the runner has an Xcode that can
  build RN 0.72.5 (see the limitations at the end).

## Splash ordering

- HarmonyOS: `entry/src/main/resources/base/profile/main_pages.json` lists
  `pages/Splash` first, and `EntryAbility.getPagePath()` returns
  `pages/Splash`; after `SPLASH_MILLIS` the page calls
  `router.replaceUrl({url: 'pages/Index'})`, so the product list has no splash
  below it in the back stack.
- Android: `SplashActivity` is the only activity with the MAIN/LAUNCHER intent
  filter; `MainActivity` keeps `singleTask` but is not exported and has no
  launcher filter.
- iOS: `UILaunchStoryboardName` points at `LaunchScreen`, and
  `AppDelegate.mm` shows `SplashViewController` for `SPLASH_MILLIS` before
  restoring the `RCTAppDelegate` root controller.

The Android and HarmonyOS splash screens were captured from the running apps
(`docs/evidence/after-android-splash.jpg`,
`docs/evidence/after-harmony-splash.jpg`). The Android recording spends about
1 s on the splash before the RN surface; the HarmonyOS recording shows the same.
The iOS splash is code-verified only (storyboard + `SplashViewController.m`
compile), because the full iOS app cannot be built on Xcode 27 here.

## Pitfalls found while wiring it

- **The official tester uses local paths; this project cannot.** `tester/harmony`
  depends on `file:../react_native_openharmony` and puts dependencies in the
  project root. Here the dependency is the registry version `0.72.140` in
  `entry/oh-package.json5`, so `ohpm install --all` runs at the `harmony/`
  root and populates `entry/oh_modules`, which is why the CMake file goes three
  levels up (`../../../oh_modules`).
- **No RNOH hvigor plugin, codegen or autolinking.** The tester's hvigor
  plugin generates `RNOHPackagesFactory`/`autolinking.cmake` for its own sample
  packages. This app uses the standalone 0.72 integration instead: the WebView
  package is registered by hand in `PackageProvider.ets`/`.cpp`, and CMake
  links its `rnoh_webview` target next to `rnoh` directly. This also removes
  the dependency on a local `react-native-harmony` checkout.
- **The WebView adaptation must be linked from its har, not its source
  directory.** With the `file:` source dependency, ohpm 26 symlinks the package
  into `node_modules/`, and hvigor then fails with
  `Failed to resolve OhmUrl` for its `index.ets`/`ts.ets`. The har dependency
  is unpacked under `harmony/oh_modules/.ohpm/…` and compiles; current ohpm has
  no `--no-link` flag. Details in [features/webview.md](features/webview.md).
- **`RNOH_C_API_ARCH=1` is required** for the CAPI architecture used by
  `Index.ets` (`enableCAPIArchitecture: true`).
- **The JS bundle is a build product.** `npm run dev` (`react-native
  bundle-harmony --dev`) writes `bundle.harmony.js` and `assets/` into
  `entry/src/main/resources/rawfile`; both are in `.gitignore`. Without the
  bundle the HAP still builds, installs and starts, but the app only shows the
  red screen `None of the provided JSBundlePath(s) ... Is Metro server
  running?`; it can only load from Metro or a sandbox copy.
- **`harmony/oh_modules` must be kept out of JS tooling.** The RNOH har ships
  its own `__tests__` (for Hermes) and `.d.ts` files generated for a newer
  TypeScript. `jest.config.js` ignores `/harmony/`, and `tsconfig.json` excludes
  it. The repo also pins TypeScript 5.4.5 because the `@types/node` pulled in by
  Jest's environment declarations uses syntax newer than the RN template's
  TypeScript 4.8.
- **SDK versions.** Only the API 26 SDK is installed here, while RNOH 0.72.140
  was built for API 12. `compatibleSdkVersion 5.0.0(12)` with
  `targetSdkVersion 6.0.0(20)` builds against the installed SDK and runs on the
  API 26 device. The C++ compile prints warnings from RNOH's own headers but
  succeeds.
- **Signing is machine- and bundle-name-specific.** The KMP signing profile is
  bound to `com.example.kmp`, so it cannot sign this app. `devecocli signature
  generate` created a `com.example.kmp.rn.harmony` debug profile; the block is
  kept in `~/.ohos/dsh-signing-rn.json5` and injected by
  `scripts/inject-signing.py` for a build. Nothing is committed.
- **Splash routing.** `pages/Splash` is first in `main_pages.json` and the
  ability's `getPagePath()` returns it. `router.replaceUrl({url: 'pages/Index'})`
  replaces the page (no back stack), so back on the product list exits the app.

## What was verified, and what was not

Verified on this machine and in the clean checkout (2026-11-13):

- `npx tsc --noEmit` and `npm test` pass, in the worktree and in the GitHub
  `js` job.
- Android `:app:assembleDebug` builds locally (Java 17, matching the runner)
  and in CI; the splash is a native activity shown for about 1 s, then the RN
  product list renders (Android 36 emulator, 1080 x 2400, light theme).
- `ohpm install --all` resolves `@rnoh/react-native-openharmony@0.72.140` from
  the ohpm registry in a clean checkout.
- `hvigorw ... assembleHap` builds unsigned from the committed profile and
  signed after `scripts/inject-signing.py`; `librnoh_app.so` compiles with the
  API 26 NDK.
- The clean signed HAP contains `resources/rawfile/bundle.harmony.js` and
  installs and runs on `FMR0224125000567` (`ALN-AL00`, HarmonyOS 7.0.0.111 /
  API 26) without the red screen: splash, then the six-product list.
- Android launcher ordering was confirmed from the built APK
  (`launchable-activity: com.example.kmp.rn.SplashActivity`), and the built
  APK has no launcher filter on `MainActivity`.
- HarmonyOS `main_pages.json` lists `pages/Splash` first;
  `EntryAbility.getPagePath()` returns it.
- The iOS `LaunchScreen.storyboard` compiles with `ibtool` and
  `SplashViewController.m` compiles against the iPhoneSimulator SDK;
  `UILaunchStoryboardName` points at `LaunchScreen` and `AppDelegate.mm` swaps
  the splash root controller after `SPLASH_MILLIS`.

Not verified:

- The iOS app was not built or run end-to-end on this machine. The installed
  Xcode is 27.0, whose minimum supported deployment target is 15.0, while the
  RN 0.72.5 template and its Pods still target 12.4. Overriding
  `IPHONEOS_DEPLOYMENT_TARGET=15.0` gets past that, but RN 0.72's Yoga and glog
  sources then fail to compile under Xcode 27's clang
  (`-Wdeprecated-literal-operator` treated as an error, and
  `_END_GOOGLE_NAMESPACE_` no longer defined). That is a pre-existing
  RN 0.72/Xcode 27 incompatibility, not something the splash change introduces;
  an Xcode 15/16 toolchain is needed to build and capture this app.
  `pod install` also needs a local workaround for RN 0.72's dead
  `boostorg.jfrog.io` URL, and the local pod install used `NO_FLIPPER=1
  USE_HERMES=0` to avoid a 480 MB Hermes download. None of those local
  workarounds are committed.
- The `ios` CI job is still skipped (`if: false` with a comment): the runner
  has Xcode 27, which cannot build RN 0.72.5 (same incompatibility as above).
  `android`, `harmony` and `js` really run; their results are in the table
  above. An Xcode 15/16 toolchain would allow enabling `ios`.
- A release HAP was not built; only the debug HAP was installed and exercised.
- RNOH 0.72.140 was exercised on an API 26 device, not on an API 12 device.
- HarmonyOS HAP signing material is intentionally absent from the repository;
  a fresh machine must generate it before building an installable HAP.
